# TruthDB: Staged Plan for Relational (SQL-Server-like) Functionality

## Context

TruthDB today implements only the start of Elasticsearch-like functionality (in-memory indices with snapshot+WAL persistence). The goal is full relational database functionality with SQL Server as the functional reference, delivered as a staged plan where **every stage compiles, passes tests, and is demonstrable end-to-end**, and the existing search functionality never regresses. The docs/ repo is deliberately disregarded.

## Decisions (all confirmed by user, 2026-07-11)

1. **Scope: full SQL Server parity, all planned in detail** (revised from the earlier "core + full SQL surface" answer): core relational engine (tables/types, CRUD, joins, aggregates, secondary indexes, ACID transactions), constraints (PK/FK/UNIQUE/CHECK/DEFAULT/NOT NULL), views, subqueries, prepared statements, **and** stored procedures/triggers/UDFs, security (logins/users/roles/permissions), backup & restore, and replication/HA — the last four as detailed stages 15–18, not outline.
2. **Hand-rolled T-SQL-flavored parser** — no sqlparser-rs.
3. **Paged on-disk table storage from day one** in the existing data region.
4. **TDS early, and TDS is *the* SQL interface**: real SQL Server tools (pymssql/go-mssqldb, later sqlcmd, SSMS query window) become the daily test harness as soon as basic SQL works. The native protocol stays a minimal dev vehicle (JSON text in `CommandResp`) and keeps carrying the ES-search surface; no native "protocol v2" is built.
5. **Recovery: full ARIES** — steal/no-force buffer management, undo logging, CLRs, fuzzy checkpoints. No transaction-size limits.
6. **Table layout: clustered index = table** (SQL Server faithful): a table with a PK is stored as a B+ tree on the PK; secondary indexes carry PK locators. PK-less tables are heaps with RID locators.
7. **Concurrency: both mechanisms, locking first** — lock-based 2PL engine first (READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE), then a dedicated stage adds a row-version store → RCSI and SNAPSHOT. End state: all five SQL Server isolation levels.
8. **Spilling in scope (SQL Server faithful)**: sort/hash operators spill to temp disk space rather than erroring.
9. **Collations: per-column via icu4x** — full plumbing (per-column collation, `COLLATE`, precedence rules) with comparison rules from the pure-Rust icu4x library (incl. Swedish/Finnish rules). Justified dependency, like rustls for TDS TLS.

**Stated assumptions (veto any):** Volcano pull-iterator executor; rule-based planner only (no cost model/histograms in detailed scope); SQL-Server-compatible error numbers from day one (102, 208, 245, 515, 547, 1205, 2627, 3902…); GO is a client-side batch separator; MARS permanently rejected; rustls for TDS TLS; single database per instance (`USE truthdb` accepted) and single `dbo` schema in detailed scope; TDS auth from config-file users only until Stage 16 migrates them into catalog logins with hashed passwords; native protocol v1 messages byte-frozen.

## Verified current state (grounding)

- Crates: `truthdb` (server bin), `crates/truthdb-core` (engine + storage), `truthdb-proto`, `truthdb-net`, `truthdb-cli`, `truthdb-bench`. Linux-only; Docker for build/test on macOS (per CLAUDE.md).
- **Protocol**: 8-byte BE header (len u32 | msg_type u16 | flags u16) + bincode payload, TCP 9623; msg types 1–6 only. Everything rides `CommandReq{id, command: String}` → `CommandResp{id, ok, message: String}`. Unknown msg types silently dropped (`dispatcher.rs:83`) hanging clients; 8 MiB frame cap.
- **Engine** (`truthdb-core/src/engine.rs`): text commands `create index` / `insert document` / `search` (ES DSL: match/term/bool). All state in BTreeMaps; persistence = full-state bincode snapshot + JSON WAL event replay.
- **Storage** (`storage.rs`, `storage_layout.rs`, `direct_io.rs`, `allocator.rs`): single preallocated file, 4096 B pages, O_DIRECT + io_uring (`DirectFile`, sync positioned I/O). Regions: header | superblocks A/B | WAL ring (256 MiB–1 GiB, CRC'd entries) | data | metadata (unused) | allocator bitmap | snapshot descriptors ×2 | reserved. `WAL_ENTRY_TYPE_COMMIT=2` reserved and already parsed; superblock reserves `metadata_root`/`data_root`.
- **Critical constraints found**:
  - Data region is monopolized by snapshot A/B *half-region slots* — `write_checkpoint` frees/reallocates half the region every checkpoint (`storage.rs:673-684`). Relational pages would be clobbered; fixing this is task #1.
  - Allocator bitmap durable only at checkpoint; between-checkpoint allocations need WAL logging.
  - WAL appends read-modify-write shared tail pages (`DirectFile::write_all_at`) — torn rewrite can destroy previously-fsynced entries (latent durability bug).
  - One fsync + superblock write **per WAL append** (`storage.rs:416-417`).
  - One global `Arc<Mutex<Engine>>`; synchronous direct-I/O inside async tasks (blocks the tokio reactor); no session state anywhere.

## Cross-cutting architecture

- **Crate/module layout**: new `crates/truthdb-sql` (pure: lexer, parser, AST with spans, type system, `Datum`, 3VL evaluator, binder via `CatalogProvider` trait, logical planner, SQL error codes) · `truthdb-core/src/relstore/` (pages, buffer pool, B+ tree, heap, row/key codecs) · `truthdb-core/src/wal/` + `txn/` (ARIES log manager, transaction/lock managers) · `truthdb-core/src/rel/` (catalog, physical planner, executors, session, results) · new `crates/truthdb-tds` (TDS frontend).
- **Command routing**: legacy ES commands all require a `{` JSON body after their prefix — that shape routes to the frozen ES path; everything else is SQL. `CREATE INDEX ix ON t(c)` has no `{`, so no collision. Router regression tests lock both grammars.
- **ARIES essentials**: every WAL record carries `{lsn, prev_lsn(txn chain), txn_id, redo + undo payloads}`; page headers carry `page_lsn`; dirty-page table + active-txn table maintained; restart = analysis → redo (repeat history) → undo with CLRs; fuzzy checkpoints (begin/end records + DPT/ATT snapshots) bound recovery time and WAL-ring reclamation.
- **Key encoding**: B+ tree keys are order-preserving byte strings (sign-flipped BE ints, IEEE total-order floats, NULL-first). String keys use **icu4x collation sort keys** as the comparable form with the original string stored in the leaf value (sort keys aren't stable across ICU upgrades — document index rebuild on major icu4x bumps).
- **LSN** = unwrapped u64 WAL byte position (current `wal_state.tail` semantics).
- **Temp space** ("tempdb-lite"): allocator extents flagged temporary, never WAL-logged, freed wholesale on restart — backs spills and the version store.

### Two practices that repeatedly caught real bugs

**Adversarially review every correctness-critical change before merging.** It
found a critical bug in *both* correctness PRs of the 2026-07-15 session, neither
findable by the author's own tests:

- #88 — validating the TDS transaction descriptor on every request would have
  killed go-mssqldb connections: v1.8.0 (the version CI pins) hardcodes a literal
  `0` on BEGIN while using the live `tranid` everywhere else.
- #89 — `TxnContext::abort` never cleared `savepoints`. Harmless for as long as
  every caller discarded the context, but the idle reaper was the first whose
  session *survives* its own abort, so a stale savepoint could silently discard
  committed rows or permanently panic a worker (there is no `catch_unwind`
  anywhere in the crate).

**Run a concurrency test's whole module 25+ times before believing it.** A
20%-flake survived *three consecutive clean full-suite runs* in #100 and was
only found by looping the module. The cause is worth knowing because it will
recur: the tests run **in parallel in one binary**, so a `static` counter used
to observe a pool measures *every other test's pool too*. Put such counters on
`Shared`, not in a static. (The one exception is a counter asserting only that
*some* pool did a thing — e.g. spawned its maintenance thread — where a sibling
satisfying it exercises the same code.)

**Prove every new test fails with its fix removed** (back up the file, weaken the
implementation, run, restore). This is not ceremony — it caught vacuous tests
three times: the ALL_HEADERS tests (the in-repo client echoed descriptors, which
real drivers do not), an `encryption = off` test (no certificate in the test
config, so the old code answered the same), and a timing test that only passed
by luck of core count (a sibling worker's stale deadline snapshot masked it — pin
such things with a single-worker pool).

Corollary: **model real drivers in test clients, not idealised ones.**

Branch → implement → adversarial review → teeth-check each test → `cargo fmt` +

Do not stop after a merge to report. Merge, branch, keep going. Surface only

### Environment and tooling gotchas

- **WSL2**: `cd truthdb && cargo test --workspace` runs natively. CI uses Rust
  1.92; the local clippy (1.94) flags test-only `let mut` / unused `path`
  warnings that CI does not — a known non-issue, not something to fix.
- **The Workflow tool's `isolation: 'worktree'` fails here.** The agent's cwd is
  the workspace root, which is not a git repo (only the subdirectories are).
  Create worktrees yourself from *inside* `truthdb/` (`git worktree add -q
  --detach <path> <sha>`) and pass each agent its own path.
- **Never give a review agent the working tree you are editing.** A review agent
  told it may experiment will edit files, and it teeth-checks by *mutating the
  fix and running the tests* — so it leaves the repo mutated while it thinks. In
  this session one such agent silently reverted the reaper fix (leaving
  `// MUTANT: no grantability skip` in the tree) and wrote its own competing
  version of a test into the same file mid-edit. Give reviewers a read-only
  brief, or their own worktree; and `git status` before trusting a test run that
  an agent was alive for.
- **Workflow `args` does not reliably carry arrays** — put lists in the script
  body. `require` is not defined in workflow scripts.
- `git add -A` inside `truthdb/` sweeps `.claude/worktrees/*` into the commit;
  add only `crates/` and `git worktree prune` afterwards.
- `git commit --amend` after a push is blocked by the sandbox. Use a follow-up
  commit.

**(a) Get the engine's housekeeping off the request workers. DONE (#99, #100).**
`worker_loop` ran `reap_expired`, `reap_idle_txns` and `drain_ready` inline, so
the engine's safety valves were only as punctual as the pool was free — and the
pool is `cores-2` threads, two on a 4-core box. Both reapers now run on a
maintenance thread that never executes a batch. The piece that made it possible
was **the inbox** (#100): the pool's `Mutex<mpsc::Receiver>` became a condvar
queue a worker waits on for *either* a call or a **drain nudge**, so a releaser
on one thread can hand parked work to a worker on another. Shutdown still works
both ways — the server calls `EngineHandle::shutdown` (`src/main.rs`), tests
just drop the handle — via a token held only by handles, since the `Arc<Inbox>`
the workers also hold can never reach zero.

Three things #98–#100 learned the hard way, all still load-bearing:

- **`reap_expired` is coupled to draining.** Reaping a victim releases the locks
  that rescue the waiters behind it, and every other releaser in `session.rs`
  drains in the same pass. A sweeper that reaps without draining re-reaps
  waiters a drain would have rescued (a chain of three loses a second victim).
  That is what the nudge exists for.
- **A grantable waiter must never drive a sleep.** #98 refuses to reap one, so
  its deadline stays in the past; a wait derived from it computes zero and
  spins. Measured at **3109 sweeps in 200ms** against the scheduler mutex — and
  only while every worker was busy, i.e. exactly when it hurts. Hence
  `earliest_reapable_deadline`, plus a floor on the sleep.
- **Workers now block indefinitely** — there is no `recv_timeout` to fall back
  on. A nudge that should have been sent and was not is a batch parked
  *forever*. Every releaser must drain directly or nudge; the maintenance sweep
  also nudges unconditionally as the backstop the old timeout used to be.

**(b) The executor half is DONE (#101).** `scan_plan` recognises a single-table
SELECT whose every output column is a source column; `scan_select` scans it in
slices, filtering and projecting each row as it is read. Peak live heap on a
50k-row table: `SELECT *` 21.4 MiB → 6.9 MiB, and `SELECT TOP 1 *` 8.4 MiB →
**158 KiB, constant in table size** where the old path was linear (16.3 ms →
0.30 ms). The result is still collected; what went is the *input's*
materialization, which is the part with no upper bound. Four gate rejections are
non-obvious and each cost a silently-wrong answer to find: `sys.*` (a quoted
`[sys.tables]` is a real, creatable user table, and resolving the catalog first
answered `SELECT * FROM sys.tables` with *its* columns); a view (no columns in
its TableDef and `root_page` 0, so a wildcard expanded to zero columns and the
scan read the catalog root); `TOP 0` (the engine raises 207/4145 *from*
evaluating the predicate, having no binding pass, so honouring TOP 0 answered an
invalid query with an empty result set); and an index seek — not rejected in the
end, because declining one threw away the TableDef/Schema/`plan::choose` that
`build_table_source` then recomputed, costing point lookups 13–23%. `TOP n`
(n > 0) stops the scan, so a predicate that would error on a row past the nth
kept one no longer raises — SQL Server's Top operator does the same.

**(c) The reply channel is PLUMBED (#103) — and it is unbounded, which is the
design, not a concession.** The bullet's own words — "bounded sinks stream
result rows" — named a design that does not work here, and this plan asserted
twice that #99/#100 had made it survivable. That was wrong — but the refutation
kills the **bound**, not the **streaming**. `UnboundedSender::send` is a plain
synchronous call: the worker never blocks, so none of the lock-holding hazards
below can arise, and the memory ceiling is the whole result — which is exactly
what the buffered path held *unconditionally, for every client*. Never worse;
bounded by what is in flight for any client that keeps up. The only thing the
bound ever bought — a hard cap against a client that stops reading entirely —
still needs cap-and-spill or Stage 13's RCSI, as before. **Lesson: when a
design is refuted, ask which specific word is wrong before concluding the whole
thing waits.**

The refutation of the bound, kept because it applies to *any* future design
that lets a client's pace reach a worker: it needs no stalled client, no
malicious client, and no bug. **A well-behaved client fetching a large result
over a normal link is enough.** With the worker `blocking_send`ing into a
bounded channel, the worker blocks *inside* the batch — which is to say **while
the batch holds its locks**, since `sched.finish` runs after
`sql_batch_with_params` returns. A 10M-row result over a slow link holds
`Table(t)` S for minutes. `LOCK_WAIT_TIMEOUT` is **5 s**. Every other session
touching that table parks, stays non-grantable for the whole transfer, and is
reaped with **1205**. There is no tuning that escapes it: the same constant
bounds a lock wait and backstops deadlock detection, so raising it past the
longest legitimate transfer means unbounded waits with no backstop. The
mechanisms, each verified against the code:

- **The stalled holder is immortal by construction.** `abort_parked_victim` opens
  with `self.parked.remove(idx)`, and `find_deadlock_victim` iterates `parked`.
  Victims are drawn *exclusively* from the parked queue. **No code path in
  `session.rs` aborts, interrupts, or reclaims locks from a running batch.** So
  the engine kills the innocent waiter and cannot touch the cause.
- **The idle reaper cannot see it** — `take_ctx` did `mem::take` on the context,
  so the session reports no open transaction and `reap_idle_txns` skips it on its
  first filter. The engine's entire answer to "a client went away holding locks"
  is disabled by exactly the scenario it exists for. #99/#100 made the reapers
  *run* off the workers; they did not make a running batch *reachable*.
- **The deadlock graph cannot represent it.** `find_deadlock_victim` builds
  `waits_for` from `parked` only, and a running batch is never a key, so it
  defaults to BLACK in `find_cycle` and cannot close a path. This is not a
  missing edge — it is a node class (the client) the graph has no identity for.
  The realistic case is a **connection pool**: conn 1 streams a result the app
  never drains because the app thread is blocked on conn 2, which wants conn 1's
  lock. A genuine deadlock through the application, invisible, and the retry loop
  that correctly answers 1205 re-parks and dies again. Livelock.
- **One stalled client plus one native command freezes the whole engine.**
  `sql_batch_with_params` holds `self.meta.read()` for the entire batch;
  `Engine::execute` (the `RunNative` path) takes `self.meta.write()`. A queued
  writer stops new readers, so *every* relational batch blocks in `meta.read()`
  regardless of which tables it touches — no lock conflict, no parking, no 1205,
  invisible to the scheduler and both reapers. (Tested with a real blocking
  `read()`, not `try_read()`.)
- **A cancel cannot free it.** A thread parked in `blocking_send` is on the
  channel's semaphore waiter list. It is not running, so it cannot poll
  `check_cancelled`; storing to an `AtomicBool` notifies nothing. Only a dropped
  `Receiver` frees it — and the draft's disconnect path does
  `cancel.store(true); let _ = (&mut work).await;`, which awaits a future that
  can never resolve. The cancel deadlocks against the thing it cancels.
  Shutdown has the same shape: `Inbox::close`'s `notify_all` wakes threads in
  `ready.wait`, and a thread in `blocking_send` is not one of them, so
  `handle.join()` blocks forever.
- **`worker_loop` strands calls.** It does `inbox.next()`, then
  `drain_ready(shared)`, and only *then* `match work`. A worker that dequeued a
  `CloseSession` and blocks inside `drain_ready` running *someone else's*
  streaming batch has that `CloseSession` on its stack — already popped, so no
  other worker can ever reach it.

**The conclusion, which is a property of this scheduler and not of the draft:**
the module header states it — *"A worker must never block in place"*, and
*"Because a running batch never waits on a lock, only parked batches can form a
lock-wait cycle"*. Streaming to a client does not add a lock wait; it adds a
**client wait**, on a node that is not in the graph, cannot be enumerated,
cannot be aborted, and has no deadline. Since locks are released only after the
batch returns, **the producer must run to completion before its locks go — so
the reply must be buffered somewhere.** A bounded channel with backpressure
contradicts that directly. **The shipped answer (#103) buffers in the channel
itself** — unbounded, so the producer finishes at its own pace and the ceiling
is the whole result, same as the old buffered path. Two designs give a *hard*
cap, if one is ever needed:

1. **Cap and spill.** A sink capped at N rows / M bytes that spills past the cap
   to temp extents, which `RowSpool` (#78) already does for the external merge
   sort. Bounded memory, no backpressure, no lock-holding stall: the producer
   runs at full speed, finishes, releases its locks, and the TDS side streams
   from the spill after `finish`. Costs first-row latency, and trades memory for
   disk.
2. **Stop holding a table S lock across the read.** This is *why* SQL Server
   survives the same client — under READ COMMITTED it releases S locks as the
   scan advances, and under RCSI readers take no S locks at all. That is Stage 13
   (version store / RCSI), which the bullet is already coupled to. Note also that
   SQL Server's default `LOCK_TIMEOUT` is **-1**: waiters wait, visibly, and the
   operator kills the head blocker. Its opt-in timeout raises **1222**, not 1205
   — 1205 is only ever a genuine cycle. TruthDB reports "you were chosen as a
   deadlock victim" for a condition that is not a deadlock.

**A pre-existing bug this uncovered, worth fixing on its own:** the 5 s → 1205
storm does **not** need streaming. *Any* batch that runs longer than 5 s — a big
scan today — already causes every concurrent session on its table to be reaped
with a 1205 that names a deadlock that never happened. Streaming would only make
the window client-controlled. The honest fix is to distinguish "blocked behind a
live holder" (wait, or report 1222) from "in a cycle" (1205).

- `BatchRender` + `stream_reply`: the renderer with the **deferred DONE**
  (streaming cannot know the last statement by index, so each DONE waits for the
  next event to settle `DONE_MORE`), and the `select!` over `events.recv()` and
  the Attention read. A channel that closes without a terminal event renders a
  clean 50000, not an empty EOM (the draft's `None => break` bug).

**Two bugs #103's review caught, both instructive:**

1. **CRITICAL — deleting `let _ = (&mut work).await;` on disconnect broke
   `take_ctx`'s invariant.** That await was the only thing keeping
   `serve_connection` from calling `close_session` while the batch still ran;
   without it, `locks.release_all` fired on a running batch and another session
   read hundreds of rows of an uncommitted transaction before its rollback. The
   `Default` placeholder context reports no open transaction, so `close_session`
   skipped the rollback too. Fix: `drain_to_end` on *both* early-exit paths
   (disconnect and the pipelined-packet protocol error). **When removing an
   `await`, ask what it was ordering.**
2. **HIGH — a late Attention's second DONE in the same message hangs
   go-mssqldb forever.** `processSingleResponse` returns at the first DONE with
   `DONE_MORE` clear and never parses behind it; `readCancelConfirmation` then
   blocks in `io.ReadFull` with `ConnTimeout` defaulting to 0. The driver's own
   comment expects the cancel ack as a **separate response** — which the same
   file already did for a standalone Attention, 250 lines up. Reproduced against
   real go-mssqldb v1.8.0 through a proxy: 3/3 hung before, 3/3 clean after. No
   conformance script sends an Attention, so conformance cannot catch this
   class. **Reason about a driver by reading it, not about it** (#88's lesson,
   repeated).

#104 fixed the #96 sliced-scan flake it exposed in CI: the test asserted a probe
thread *won* the storage lock mid-scan, but `std::sync::Mutex` is not fair, so
that asserts the scheduler's behaviour (~35% failure under load). It now asserts
the deterministic mechanism — the scan acquires the lock once per slice, which a
non-reentrant mutex cannot do without releasing between slices. **Never assert
that another thread wins an unfair mutex.**

**The last leg shipped in #105** — statements emit their events as they run —
and its adversarial review (four lenses in their own worktrees, every finding
refuted independently by two agents before being believed) caught three real
defects, each a lesson worth keeping:

1. **Commit-derived state escapes through rows, not just DONEs.** The first cut
   fsynced before a rowset opened only when some *DONE* acknowledged a commit —
   but an identity value reserved by an in-transaction INSERT (a mini-commit)
   leaves through the *rows* of the next `SELECT SCOPE_IDENTITY()`, and a crash
   then rewinds the counter and reissues a value the client observed. The flush
   now gates on the same kind-based `committed` flag as the batch-end fsync.
2. **`DONE_ERROR` with no ERROR token means "severe failure, discard results"
   to every real driver** — pytds raises "Request failed, server didn't send
   error message" (reproduced live against the built server), go-mssqldb
   v1.8.0 synthesizes "Request failed but didn't provide reason" and strands
   the result sets behind it, and SqlClient's equivalent branch covers server
   aborts. So a statement that fails after its rows started streaming closes
   its set with a **clean** DONE (`StatementAborted`); the error text still
   travels as the batch-final ERROR token, and a caught error surfaces
   nothing. The conformance scripts now run the caught / empty-CATCH /
   continued shapes against both real drivers in CI.
3. **Every early exit from `stream_reply` must cancel and then drain.** The
   io-error exits (a socket write failing mid-render — the ordinary way a
   client dies mid-query, newly reachable once rows stream during execution)
   returned without either, so `close_session` released a *running* batch's
   table locks and another session could read its uncommitted writes. Third
   instance of this class (#103's disconnect bug, the pipelined-packet arm):
   when a path leaves `stream_reply`, ask what still holds locks.

The wire change it forced, decided deliberately: each DONE carries its own
statement's `in_transaction` (`BEGIN TRAN; SELECT 1; COMMIT` reads INXACT
1,1,0); `Complete{in_transaction}` stays batch-final — `handle_tm_request`
reads it to decide whether a terminating ENVCHANGE fires (#88). Durability
kept its ordering through deferred DONEs: they queue and flush — fsyncing
first iff any statement since the last durability point may have committed —
before the next result set opens and at batch end, so a write-only batch still
costs one fsync and nothing client-visible precedes the fsync standing behind
it.

**The generalisable lesson, now paid for twice:** the scheduler's liveness
quietly assumes a worker returns promptly, and *anything* that lets a client
delay a worker breaks assumptions written years apart. #98 fixed one that was
already latent (`reap_expired` killed a waiter that was grantable-but-unrun past
its deadline, reporting 1205 with no conflict). **And a design in this plan is a
claim, not an instruction** — this bullet said "bounded sinks" for months and
twice asserted the blocker was cleared. It was refuted by reading the code it
would run on. Audit a design against the code before building it, exactly as you
would a gap note.

- ✅ Row versioning — **done (#120), with the design refuted on audit**: the sketched row-carried version pointer + temp-extent store cannot land in this storage (the positional row codec has no header and rejects trailing bytes — the #115 finding again; deletes are physical, so a version must be reachable without its row), and version state has **no durability requirement at all** (no snapshot survives a restart, so an empty store is correct by construction). Shipped instead: an in-memory version store (`relstore/version.rs`) — per-table chains keyed by row identity (clustered key bytes / heap home RID), newest-first, head = current physical state, older entries carry images; commit-sequence table with snapshots = the **durable commit prefix** (a committed-but-unfsynced writer is invisible, preserving the no-lost-reads property lock release already gives); publication under the same storage-mutex hold as the page mutations; rollback (full and to-savepoint) reverses publications exactly; the maintenance thread prunes below the watermark (oldest live snapshot, else current durable seq) and drops dropped tables' chains.
- ✅ `ALTER DATABASE {name|CURRENT} SET READ_COMMITTED_SNAPSHOT / ALLOW_SNAPSHOT_ISOLATION {ON|OFF}` — **done (#120 + #121)**, persisted in the superblock reserved area (checkpoints carry it; the ALTER takes Database X, flips memory only after both superblock writes fsync, and **refuses with 5061 while any transaction snapshot is registered** — an idle SNAPSHOT transaction holds no locks between batches, so Database X alone does not prove quiescence; SQL Server waits instead, #121's review caught the debug-panic/release-corruption). RCSI (#120): a READ COMMITTED SELECT captures a per-statement snapshot, takes Database IS only (no Table S), reads atomically under one storage-lock hold, and merges the version store on scans AND index seeks (covering included; the executor's full-WHERE re-check filters over-returns). SNAPSHOT isolation (#121): `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` (TDS byte 5), one view per transaction captured at first data access and released on every ending path; 3952 at access when not allowed; UPDATE/DELETE target the SNAPSHOT's rows with 3960 on rows a snapshot-invisible writer changed or deleted (the transaction rolled back entirely, as SQL Server aborts it) and no targeting of rows matching only their current version; 3961 via schema stamps on ALTER ADD **and CREATE TABLE** (the review's DROP+CREATE same-name evasion). DML's reads under RC stay lock-based, and SI `INSERT...SELECT` keeps a redundant source Table S — documented conservative divergences. Both PRs' adversarial reviews found real seam defects (seven total, three by live dirty-read/panic repro: the EXEC-literal isolation collapse, parked-batch lock sets stale across an option flip — fixed with a lock-analysis epoch + re-analysis at grant — and the ALTER-under-live-snapshot reset); all fixed with the repros kept as regressions.
- ✅ Exit — **done (#120 + #121)**: readers-don't-block pinned by value at session level AND over a real driver; write-conflict tests (3960 both shapes, conflict-free inverse); version cleanup under load (a live snapshot pins exactly its history through churn — reading its consistent view throughout — and release lets the prune drop the store); all five isolation levels adjudicated by pytds in CI (`scripts/tds_isolation_matrix.py`: RU dirty-reads, RC/RR wait for the commit, RCSI answers pre-update values without waiting, SNAPSHOT repeats reads and answers 3960/3952) plus slt files for the single-session surfaces.

### Stage 14 — SSMS query window + large values + ops hardening
- ✅ SSMS scope = query window — **done (#122)**: `SERVERPROPERTY` (argument-value dispatch with session context — a third eval shape; unknown properties NULL like SQL Server), `sys.databases` (one row, live versioning flags) + minimal `sys.configurations` (INT values where SQL Server uses sql_variant — documented), `USE` with the database ENVCHANGE + 5701 INFO in SQL Server's exact token order (prior DONEs flush first — the review caught the jump), `SET NOCOUNT` honored on every client protocol (TDS DONE_COUNT dropped, native count envelope quiet like sqlcmd; @@ROWCOUNT untouched), and per-statement DONE_COUNT made accurate: real `@@ROWCOUNT` (was hardwired 0 — SELECT/DML/assignment-SELECT counts, simple `SET @x=` sets 1, bare DECLARE preserves, failed statements — including failed EXECs, a review catch — reset 0), assignment SELECTs now carry their processed-row count. - ✅ Overflow page chains for values > in-row cap (VARCHAR(MAX)-class) + TDS PLP encoding — **done (#123)**: explicit `*Max` type variants (catalog round-trips them as `varchar(max)` name strings — old files untouched); values over a 256-byte inline threshold live in immutable overflow chains (new page type, WAL system images like split pages; failed/superseded chains LEAK — the dropped-table posture, checkpoint-vacuum is future work — and that immutability is what keeps version images holding chain REFERENCES resolvable forever); row codec stores MAX values behind a schema-driven tag byte; every read path resolves references before rows escape (an escape is a loud internal error); **version priors switched to raw physical pre-images for ALL tables** (tree op returns / heap pre-reads — a re-encode would have re-inlined 10 MiB into the 64 KiB var cap; the review verified this on both engines incl. forwarded heap rows); (MAX) rejected as PK/index key/INCLUDE (1919; INCLUDE is a divergence — our include payloads live under the tree cell cap); COLMETADATA 0xFFFF + PLP framing byte-pinned, adjudicated live by pytds (99k chars both directions in CI; the review pushed to 512 KB VARBINARY and 10 MiB through packet chunking). Review's confirmed finding fixed: ALTER ADD now re-spills MAX values inside its rewrite statement (it re-inlined or failed before). Exit pins: 10 MiB round-trip + kill-and-reopen with an in-flight update undone; RCSI reads the pre-update big value through its image's reference. Offline file growth shipped (#124): `truthdb-cli grow --path <file> --add-gib N` on a STOPPED server — the data region ends where the tail regions begin, so growth shifts the tail right; crash safety is a SIZE FLOOR, not ordering (the delta must clear the tail's whole span, putting every relocated write in the fresh extension; the header stamps last, fsync-fenced, the v1→v2 commit-point pattern; a crash before the stamp leaves the old layout fully valid and a re-run completes it). The bitmap is copied with zero (= free) extension bits so pending WAL replays on top unchanged. ### Stage 15 — T-SQL programmability: stored procedures, triggers, UDFs
- ❌ Grammar: `BEGIN...END`, `IF/ELSE`, `WHILE/BREAK/CONTINUE`, `RETURN [expr]`, `TRY/CATCH`, `THROW`, `RAISERROR` (printf subset); `CREATE/ALTER/DROP PROCEDURE` (param defaults, `OUTPUT`), `EXEC [@rc =] name` (positional/named/OUTPUT args); `CREATE FUNCTION` scalar + inline TVF + multi-statement TVF; `CREATE TRIGGER ... AFTER {INSERT,UPDATE,DELETE}` with `inserted`/`deleted` and `UPDATE(col)`. Deferred with justification: INSTEAD OF triggers, GOTO, cursors.
- ❌ Execution: **AST interpreter + per-statement cached plans** (what SQL Server does). Body parsed into a `ProcBody` control-flow tree; leaf statements bound/planned lazily, cached, stamped with catalog version (reuses prepared-statement rebind machinery). Engine `ProcCache` by object_id; per-session frame stack (`@@NESTLEVEL` cap 32 → error 217, recursion within cap); `@@ERROR`/`@@ROWCOUNT` maintained by the dispatch loop.
- ❌ Error semantics faithful: severity 11–19 catchable, ≤10 informational, ≥20 kills the connection; `XACT_ABORT`/doomed transactions give `XACT_STATE() = -1` (CATCH may only ROLLBACK) riding ARIES statement/txn undo. Build the severity/abort truth table first — it's the subtle core.
- ❌ Triggers: fire once per statement (incl. 0-row, faithful), creation order, `inserted`/`deleted` rowsets spill to temp extents, run inside the statement's txn (`ROLLBACK` in trigger → 3609); nested-triggers ON / RECURSIVE_TRIGGERS OFF defaults. Scalar UDFs run per-row (no inlining — documented perf cost); side-effect restrictions enforced in binder.
- ❌ Catalog: `sys.procedures/triggers/trigger_events/parameters` over `sys.objects`; objects gain an owner `principal_id` now (Stage 16 hook) and a stubbed `PermissionChecker` trait. TDS: RPC-by-name to user procs, RETURNSTATUS + RETURNVALUE tokens, exact DONEINPROC/DONEPROC counts.
- ❌ Exit: TRY/CATCH × severity × XACT_ABORT slt matrices; trigger suites (0-row fire, rollback-in-trigger, nesting caps, spill path); OUTPUT/return-status conformance from real drivers; kill-mid-trigger crash test (statement fully undone).

### Stage 16 — Security: logins, users, roles, permissions
- ❌ Authentication: `CREATE/ALTER/DROP LOGIN ... WITH PASSWORD`, **PBKDF2-HMAC-SHA256** (210k iterations, salted, versioned blob) using the crypto provider rustls already brings into the tree (zero new compiled deps; deliberately not SQL Server's hash format — security beats faithfulness, documented). Verification off the engine-actor thread. First boot migrates `[tds.auth]` config users into `sys.server_principals` and always ensures `sa`; config auth is then dead. In-memory per-login/IP login backoff; 18456 with faithful state codes.
- ❌ Principals: **both levels kept** (logins + database users, `dbo`↔`sa`) — SSMS and `SUSER_SNAME()`/`USER_NAME()` semantics assume it. Server role `sysadmin` (bypass-all); fixed db roles `db_owner/db_datareader/db_datawriter/db_ddladmin`; user-defined roles with nesting (cycle-checked). Effective membership = cached bitset with a **security version counter** bumped by security DDL.
- ❌ Permissions: `GRANT/DENY/REVOKE {SELECT,INSERT,UPDATE,DELETE,EXECUTE,REFERENCES,ALTER}` on objects + database-scoped `CREATE ...` grants; DENY beats GRANT across user + transitive roles. Column-level grants and `WITH GRANT OPTION` deferred (documented complexity cliff).
- ❌ Enforcement **in the binder**: plans carry a `RequiredPermissions` set + security version, revalidated on reuse when the version moves (closes the stale-plan bypass). **Ownership chaining implemented** (skip check when owner(A)==owner(B)) — makes the grant-EXECUTE-only app pattern work.
- ❌ Catalog: `sys.server_principals/sql_logins/database_principals/database_role_members/database_permissions`; `SUSER_SNAME`, `USER_NAME`, `IS_SRVROLEMEMBER`, `IS_ROLEMEMBER` intrinsics.
- ❌ Exit: PBKDF2 test vectors; DENY/GRANT truth-table slt across nested roles; ownership-chain scenarios (proc→view→table); revoke-then-reuse-cached-plan test; driver login conformance incl. backoff timing; config-migration upgrade test.

### Stage 17 — Backup & restore
- ❌ **Online fuzzy full backup** (ARIES-bracketed): force fuzzy checkpoint → `redo_start_lsn`; register a hold in a new **`LogTruncationGate`** (truncation floor = min over checkpoint/backup/log-backup/replication-slot holds — built here, reused by Stage 18); copy allocated pages in physical order (checksum-verify each, retry, buffer-pool fallback for torn reads); a concurrent **log follower** streams WAL entries into the backup so the hold trails rather than pinning the window; capture `backup_end_lsn`; fail clean (3013-style) if ring pressure would overwrite unshipped log. Search snapshot region copied as a raw extent — same LSN space, so log coverage is automatic.
- ❌ Recovery models: `ALTER DATABASE ... SET RECOVERY {FULL|SIMPLE}`. FULL holds ring truncation until `BACKUP LOG` copies `[last_log_backup_lsn, end]` to archive files (copy-out-before-truncate); no log backup + full ring ⇒ 9002 stall, faithful and documented.
- ❌ **Restore is offline via CLI** (`truthdb-cli restore --full f.bak [--log ...] [--stopat TS]`): rebuild a fresh file from page images + allocation map, ARIES redo of embedded+archived log, PITR stop at commit timestamp (commit records gain a timestamp field), undo in-flight txns. `RESTORE VERIFYONLY/HEADERONLY/FILELISTONLY` online over TDS; full T-SQL `RESTORE DATABASE` returns "instance must be offline" (single-db instance — documented simplification).
- ❌ Format `TDBBAK1`: self-describing header, allocation map, page-run blocks, 64 KiB log blocks, xxh64 on every block; `WITH INIT / CHECKSUM (default on) / STATS / COPY_ONLY`; compression codec byte reserved (lz4_flex later); DIFFERENTIAL/striping/encryption deferred. Minimal `sys.backupset` history table (file is self-describing, history loss non-fatal).
- ❌ Exit: backup-under-concurrent-write-load → restore → logical-dump diff; kill-mid-backup harmless; PITR between two marked commits; log-chain gap detection (4305); VERIFYONLY on bit-flipped fixtures; FULL-model ring-stall test.

### Stage 18 — Replication / HA (physical WAL shipping)
- ❌ **Physical, not logical**: standby applies ARIES redo verbatim → byte-identical replica, search subsystem replicated for free. Availability-group-lite: topology via config + CLI, not the enormous AG DDL (documented).
- ❌ Transport: replication listener (default 9624), TLS mandatory (rustls reuse), shared-secret auth; messages `Hello{node_id, cluster_uuid, epoch, last_received_lsn}` / `LogData` / `FlushAck{flushed_lsn, applied_lsn}` / `Heartbeat` / `Promoted`.
- ❌ Standby lifecycle: seeded from a Stage 17 backup restored `--standby`; **perpetual incremental redo** (restart redo refactored into a resumable LSN-range function with restartpoints). Per-standby **persistent slots** hold ring truncation via the `LogTruncationGate`; `max_slot_retain_bytes` exceeded ⇒ slot invalidated, standby must reseed.
- ❌ **D1 (async + manual failover)**: log-writer hands flushed ranges to per-standby sender threads; `truthdb-cli promote` (T-SQL alias `ALTER DATABASE ... FAILOVER`): drain, finish redo+undo, bump the new **epoch** field in the superblock, open read-write. Epoch fencing rejects lower-epoch streams; a diverged old primary must reseed (no pg_rewind analog — documented). No auto-failover/quorum in scope.
- ❌ **D2 (sync + readable standby)**: per-replica `SYNCHRONOUS_COMMIT` — group commit additionally waits for `FlushAck ≥ batch_end_lsn` (pending queue in the log-writer); ack timeout ⇒ replica NOT_SYNCHRONIZED, commits proceed (availability-first, documented, with a strictness knob). Readable standby: redo writes pre-images into the standby's **local** version store; reads are SNAPSHOT-only at the last-applied-commit LSN (same approach as SQL Server readable secondaries; depends on Stage 13).
- ❌ Monitoring: `sys.dm_repl_replica_states` / `sys.dm_repl_slots` virtual tables + `truthdb-cli repl-status`.
- ❌ Exit: two-process CI harness — standby kill/reconnect resumes from `last_received_lsn`; primary kill → promote → slt verification; sync-commit fault injection (delayed acks block commits, then timeout demotion); slot invalidation under ring pressure; epoch-fencing rejoin refusal; lag-metric assertions.

## Search-engine coexistence (every stage)

Search WAL events keep `entry_type=1` JSON payloads and existing replay; relational records use new entry types; recovery demultiplexes by type from one ring. Search snapshots keep the descriptor mechanism (placement changes to allocator extents in Stage 1). Combined checkpoint ensures `wal_head` never passes a record either subsystem needs. The ES DSL grammar is frozen; router regression tests guard both surfaces. Search stays reachable only via the native protocol until full-text convergence.

- **Parser corpus** (Stage 3+): golden `.sql` → AST/error files; every bug becomes a corpus file.
- **Crash/recovery harness** (Stage 2+): kill-without-checkpoint, reopen, assert exactly-committed state; ARIES-specific: undo-with-CLRs, crash-during-recovery, torn-page FPI repair.
- **slt runner** (Stage 8+): hand-rolled sqllogictest-format files driving `Session::execute_batch` in-process.
- **Plan goldens** (Stage 7+): SHOWPLAN_TEXT snapshots.
- **TDS conformance** (Stage 4+): CI jobs with real drivers (pymssql, go-mssqldb, go-sqlcmd, ODBC sqlcmd, JDBC) against a live server; byte-fixture tests for every packet/token/type codec.
- **Collation tests** (Stage 5+): Swedish/Finnish ordering goldens; sort-key/index-order consistency.

## Key risks

1. **Full ARIES is the hardest subsystem** (undo chains, CLRs, fuzzy checkpoints, ring-WAL interaction) and it lands early (Stages 1–2) because everything sits on it. Mitigation: exhaustive crash-harness matrix before any SQL lands; keep the old WAL path behind a test flag until crash tests pass.
2. **Stage 6 engine-actor refactor** touches every request path — sequenced while locks are table-granular and interleavings coarse.
3. **TDS-early means codec churn**: TYPE_INFO codecs grow with each type stage; byte fixtures per codec keep this mechanical. Tunneled TLS-in-PRELOGIN (Stage 9) is ~200 careful lines — fixture-test against captured handshakes.
4. **Collation-aware keys** couple icu4x sort keys to index layout — original values stored in leaves; index rebuild documented for icu4x major upgrades.
5. **DECIMAL arithmetic and datetime encodings** are fiddly pure-code sinks — goldens cross-checked against SQL Server documentation.
6. **Interface churn between SQL and storage**: `TableAccess`/`IndexAccess` traits + row/key codecs co-signed at Stage 2 exit; everything above is insulated.
7. **TRY/CATCH × statement-atomicity semantics** (Stage 15): which errors doom a transaction is the subtlest T-SQL behavior to replicate — build the severity/abort truth table first and test it exhaustively.
8. **Resumable-redo refactor** (Stage 18) touches restart correctness, and standby redo-generated row versioning is the hardest replication piece — both isolated behind the D1/D2 split.

- **#90 — Stage 8 ORDER BY resolution on the plain path (aliases + ordinals).** Two query-correctness bugs, neither in any gap note — both found by auditing this plan against the code. The grouped/DISTINCT paths project first and resolve ORDER BY against the output names; the plain path sorts *source* rows against a `JoinScope` of base columns only, so it could see neither. (1) **SELECT-list aliases were invisible**: `SELECT v AS vv FROM a ORDER BY vv` → 207, though ORDER BY is the one clause where an alias is in scope; worst for an alias over a computed expression (`SELECT v*2 AS dbl ... ORDER BY dbl`), which has no base column to fall back on and so could not be written at all. (2) **`ORDER BY <ordinal>` was a silent no-op**: the integer evaluated as a *constant*, so every sort key tied and the stable sort returned insertion order — no error, just the wrong order (worse than the alias bug, which at least failed loudly). Both now rewrite before sorting to the expression they name — an alias to its select-list expression, an ordinal to its output column's — which preserves the path's ability to order by a base column that was never selected (the reason it sorts pre-projection). Edges match SQL Server: an alias shadows a same-named base column; a qualified `a.v` always means the table's column; a self-referential alias (`SELECT v+1 AS v ... ORDER BY v`) substitutes once, not recursively (`map_expr_columns` does not rescan a substitution); an out-of-range ordinal is 108. Wildcard ordinals expand to *qualified* source references, so `SELECT * FROM p JOIN q ... ORDER BY 2` stays unambiguous when both tables share a column name rather than trading a silent mis-sort for a 209. Every case was verified to fail with its fix removed.
- **#89 — Stage 6 idle-transaction reaper.** Sessions stamp `last_activity` (on dequeue, dispatch and finish); the worker loop sweeps sessions idle past `idle_txn_timeout` (default 10 min, `Option` so it can be disabled) that still hold a transaction, rolling it back and releasing its locks, then draining what that unblocks. Only genuinely idle sessions are candidates — a running batch has had its context moved out by `take_ctx`, so it reports no open transaction and cannot be reaped mid-batch; a parked batch's session is skipped (waiting on locks, not abandoned). The wake cadence had to be fixed for the sweep to be on time: a worker slept to the nearest parked deadline ignoring the periodic cap, and the cap itself only considered `lock_wait_timeout`; it now wakes for whichever duty comes first (defaults unchanged, the 5 s lock-wait bound still dominates). **Adversarial review (25 agents) caught a critical bug the reaper made reachable**: `TxnContext::abort` cleared txn/trancount/doomed but never `savepoints` — invisible because every existing caller discards the context immediately (`close_session` removes the Session, `finish` drops it). The reaper is the first caller whose session *survives and keeps using* its context, so a savepoint holding the dead transaction's undo-log offset leaked into the next one: `ROLLBACK TRANSACTION <name>` then found the stale name instead of erroring 3908 and handed a dead offset to `rel_rollback_to`, which either truncated the new transaction's undo log (silently discarding committed rows) or panicked in `Vec::split_off` — killing the worker permanently, since the crate has no `catch_unwind`, and leaking that session's locks. `abort()` now clears savepoints, closing the same latent hole in `abort_parked_victim`. Review also caught that a reaped session was left indistinguishable from one that never began a transaction, so a returning client's statements **silently autocommitted**; the reap is now reported to the next batch as 1205 (the code already used for a server-initiated abort, which drivers retry). Review further showed three guards were untested and one test vacuous: the guards are now pinned deterministically against a bare `Scheduler` with a zero idle timeout (and each test proven non-vacuous by showing the same session *is* reaped once the guard's condition lifts), and the cadence fix by a **single-worker** test — with several workers a sibling's stale deadline snapshot sweeps anyway and hides a too-long wait. Every new test was verified to fail with its fix removed; no flakes over 25 runs nor under 8-way CPU load.
- **#88 — Stage 6 ALL_HEADERS + transaction-descriptor validation.** The Stage 6 TDS bullet asked for TM requests "validated in ALL_HEADERS"; the block was skipped instead. `skip_all_headers` read only the leading `TotalLength` and, when out of range, treated the payload as having no headers — handing the header bytes to the SQL/RPC decoder as the request; it never walked individual headers. `parse_all_headers` now validates the whole block (MS-TDS 2.2.5.2) and extracts the type-2 descriptor; malformed ⇒ protocol error. The request loop parses once per SQLBatch/RPC/TM and passes the body down, so `run_rpc`/`parse_tm_request`/`batch_sql` take an already-stripped body. **Adversarial review caught a critical interop bug**: validating the descriptor on *every* TM request breaks go-mssqldb v1.8.0 — the version CI pins — whose `sendBeginRequest` hardcodes `transDescrHdr{0, 1}` while `sendCommitRequest`/`sendRollbackRequest`/`sendQuery` use the live `sess.tranid`. A begin's descriptor is a placeholder, so after a batch-path commit left the server's descriptor non-zero, the next begin claimed 0 and was rejected, killing a correct client's connection. Only COMMIT/ROLLBACK are validated now. Review also confirmed a latent bug the validation made load-bearing: a nested commit (@@TRANCOUNT 2→1) emitted ENVCHANGE 9 and zeroed the descriptor while ignoring `reply.in_transaction` — the reply contradicted its own DONE(INXACT); a terminating ENVCHANGE now fires only when the transaction actually ends. The tests missed both because the test client echoed the descriptor everywhere; it now models go-mssqldb's asymmetry. Both regressions are pinned by tests **verified to fail without their fix**, and CI's real go-mssqldb conformance job passes.
- **#87 — Stage 6 TRY/CATCH + `XACT_STATE()` + `ERROR_*()`.** T-SQL structured error handling on the `rollback_to` savepoint primitive from #83. `BEGIN TRY … END TRY BEGIN CATCH … END CATCH` parses to `Statement::TryCatch`; the batch loop became a recursive `run_block(.., in_try)` — inside a `TRY` *any* statement error transfers to the matching `CATCH` (returned as `Err`), outside one the existing XACT_ABORT policy is untouched. The failed statement's writes are already undone to its per-statement savepoint, so the `CATCH` sees a consistent transaction; `SET XACT_ABORT ON` (or severity ≥ 17) still dooms the txn but control still reaches the `CATCH`, where `XACT_STATE()` reports -1. A TDS Attention is never catchable — it aborts the batch past any `TRY`. The `CATCH` runs in the *enclosing* try-context, so its own errors propagate to an outer `CATCH`; caught errors push on a stack so nested TRY/CATCH restore the outer error for `ERROR_NUMBER/MESSAGE/SEVERITY/STATE`. **The doomed gate was corrected to SQL Server semantics**: an uncommittable transaction rejects *log writes* with 3930 but still allows reads/`SET`/`DECLARE` — it previously rejected everything but ROLLBACK, which would have made `SELECT XACT_STATE()` inside a doomed `CATCH` (its whole purpose) impossible; a partial ROLLBACK and `SAVE` stay rejected. Lock analysis flattens TRY/CATCH so statements nested in blocks still pre-acquire their table locks. Two adversarial reviews: control-flow found **no bugs** (verifying cancel-not-caught, doomed-CATCH reads, nested error-stack scoping, commit-in-CATCH durability and savepoint isolation empirically); integration found a **real parser bug** — with no reserved-word set the alias parsers read a bare `END` as an implicit alias, so the *canonical* semicolon-less form (`SELECT 1 END TRY`) failed with 102, and every test passed only because they used semicolons. `END` is reserved in T-SQL and is now declined as a bare alias (`AS end`/`[end]` still alias), with parser + end-to-end regression tests. Gaps: `ERROR_LINE()` reports 0 and `ERROR_PROCEDURE()` NULL (no statement-line map, no stored procedures yet).
- **#86 — Stage 4 TDS Attention (cancel) mid-statement abort.** An Attention was only acknowledged; the batch ran to completion. Now it cancels the running statement: a thread-local cancel flag (`CancelScope`, cleared on drop) threaded connection → engine actor → worker, polled by `check_cancelled()` in the executor's per-row loops (exec_select filter, hash-join build+probe, grace-hash join, nested-loop join, ORDER BY sort, GROUP BY grouping, UPDATE/DELETE/INSERT). The server's `run_watching_attention` runs the batch while concurrently watching the socket — `AsyncReadExt::read` is cancellation-safe, a partial header is completed afterward so framing stays intact — and answers `DONE(attention)`; a pipelined non-Attention packet mid-batch is a protocol error. A cancelled statement aborts the batch (internal error 3617) but leaves the transaction open (not doomed). Two adversarial reviews (async/framing — clean; engine lifecycle/coverage): fixed the abort guard to key on the cancel error number (not the raw flag, so a concurrent Attention can't suppress unrelated `XACT_ABORT` dooming) and widened the poll set to hash-join/sort/aggregate/DML. Known limitation: a parked (lock-blocked) batch or a single monolithic `rel_scan` cancels with latency.
- **#85 — Stage 2 fuzzy checkpoints.** Checkpoints were quiescent — refused while any explicit transaction was open (truncating the WAL head to the tail would discard undo an open txn needs for crash rollback). Now they are **fuzzy**: they run with open transactions, flushing dirty (incl. uncommitted) pages under the steal policy but clamping `wal_head` to the **oldest open transaction's begin LSN** (`RelState` now tracks per-txn begin LSNs), so every open txn's redo+undo survives. `checkpoint_if_quiescent`→`checkpoint_if_wal_full` (active-txn gate dropped). The shared WAL ring is safe because ES replay filters by snapshot sequence, not `wal_head`. Crash-tested (open-txn-then-crash undoes; work-across-checkpoint-then-commit survives) + 3-lens durability review, zero findings.
- **#84 — Stage 6 `SAVE TRANSACTION` / `ROLLBACK TRANSACTION <name>`.** Named savepoints, reusing the `rollback_to` primitive from #83. `SAVE TRANSACTION <name>` records a savepoint per open transaction; `ROLLBACK TRANSACTION <name>` partially rolls back to it (the transaction stays open, `@@TRANCOUNT` unchanged), invalidating later savepoints and erroring 3908 for an unknown name. Savepoints clear on the outermost COMMIT / full ROLLBACK; a doomed transaction rejects `SAVE`/partial `ROLLBACK` (only a full ROLLBACK). The parser now captures the optional name after `ROLLBACK [TRAN]` and requires one after `SAVE TRAN`. Tested including a **crash-mid-transaction recovery** through a `ROLLBACK TO` savepoint.
- **#83 — Stage 6 statement-level atomicity + `SET XACT_ABORT`.** The engine behaved as if `XACT_ABORT` were permanently ON — *any* statement error doomed the whole transaction. Added a real ARIES savepoint: `rollback_to(savepoint)` (relstore/recovery.rs) undoes the undo-log *suffix* via the existing `undo_one`/CLR discipline (sealing CLR `undo_next` = the undone op's predecessor), so it is crash-safe by construction — a crash after a partial rollback recovers without double-undo (the compensated statement is skipped via the CLR chain). `rel_statement_scoped` now savepoints before every explicit-txn statement and rolls back to it on error, so a failed statement undoes only its own writes (a partial multi-row INSERT undoes *all* its rows). `execute_batch_with_params` then honours `SET XACT_ABORT`: OFF (the default) with a non-fatal error (severity < 17 — constraint violations are 14–16) rolls back just the statement and the batch continues; ON, or severity ≥ 17, dooms the transaction (only ROLLBACK, error 3930). Tested for statement/multi-row atomicity, XACT_ABORT ON vs OFF, and **crash-mid-transaction recovery** after a statement rollback. Remaining: TRY/CATCH, `XACT_STATE()` (both can reuse `rollback_to`; `SAVE TRANSACTION` shipped in #84).
- **#82 — Stage 5 collation-aware (case-insensitive) equality.** The default collation is `_CI_AS`, so string equality now folds case *consistently* — the engine was self-contradictory before (`ORDER BY name` folded case but `WHERE name = 'ABC'`, `GROUP BY`, joins, and uniqueness did not). Query layer: `eval` compares via `compare_collated` (WHERE/JOIN/IN/BETWEEN/LIKE), hash operators fold their key strings (GROUP BY/DISTINCT/hash-join, keeping the original value for output), MIN/MAX/COUNT(DISTINCT) fold. Storage layer: character **key bytes** are folded (`key.rs::fold_key_datum`) across the clustered PK, secondary indexes, index seeks, `rel_get`, FK probes (fast-path *and* the Datum-value scan fallback), and the row-lock hash — so seeks, PK/UNIQUE, and FK all match case-insensitively, and CI-equal point-writers re-serialize on one row lock (the previously-flagged row-lock coupling is thus *resolved*, not merely guarded). Explicit `_CS`/`_BIN` columns stay exact (simplified precedence: any `_CS` operand forces exact). A CI/CS matrix + restart test is the safety net; SLT corpus unchanged. Adversarial review + a verification sweep caught **ten** fold-consistency bugs pre-merge — each a *store-side folds but this lookup/predicate doesn't* miss: the grace-hash GROUP BY spill partitioning, the `Vec<String>` resolver in UPDATE/DELETE/CHECK (a `_CS` data-loss bug), the aggregate HAVING/projection synth resolver, the self-ref FK batch (INSERT) and snapshot (UPDATE) paths, the mixed-collation FK fast path, and DISTINCT ignoring `_CS` — all fixed and regression-tested. The forward coupling this closes was flagged in the previous session's decisions. Not done: icu4x **sort keys in index keys** for locale *ordering* / `_AI` (dependency-blocked); two narrow edges documented in-code (an ambiguous cross-source `SELECT DISTINCT a.col` name, and a `_CS` equality *embedded in* an ORDER BY expression, both fall back to case-insensitive).
- **#81 — Stage 8 grace-hash for LEFT/RIGHT/FULL joins + DISTINCT.** The grace-hash INNER join was generalized to all outer kinds: the non-driving side is the build side (left for RIGHT, else right), output is always `[left..right]`, unmatched probe rows are null-extended (LEFT/RIGHT/FULL), unmatched build rows too (FULL), and NULL-keyed rows are null-extended on the outer side / dropped on the inner side. `DISTINCT` past budget partitions rows by row-hash and dedups each partition, bounding the dedup set. A/B force-spill tests assert byte-identical results to the in-memory path for all three outer kinds and for DISTINCT. **The Stage 8 spill story (sort + agg + all joins + DISTINCT) is now complete** except for streaming scans (input materialization).

Still open after this session (candidates for the next pass, hardest/most-valuable first): Stage 8 **streaming scans** so the input isn't fully materialized (the operators now bound their own working set, but `build_source` still materializes the input); Stage 12 **key-range locks** + partitioned lock manager; Stage 5 icu4x **sort keys in index keys** for locale-specific *ordering* and `_AI` accent-insensitivity (blocked by `icu_collator` 1.5 exposing no public sort-key byte API — case-insensitive *equality* is now done in #82); Stage 9 **`sp_prepare` family** + prepared-statement rebind; `ALTER TABLE ADD column` is **not** a quick item — `decode_row` is strict, so it needs a self-describing row format or a full-table rewrite.

#### Design decisions (why the forks went the way they did)

The directive for the session was *choose performance at every fork; don't shy from complexity.* The load-bearing choices:

1. **Stage 8 — in-memory hashing before spill.** (a) full spill-capable operators vs (b) in-memory hash join/agg/distinct first. Chose **(b)** — the O(n²)/O(n·m) algorithms were the actual bottleneck and the dominant real-world win; the executor is fully materialized (inputs already in RAM) and `allocate_temp_extent` has zero production callers, so spill is a large greenfield disk-page layer left as the top follow-up.
2. **Stage 12 — up-front point-key row locks, not mid-scan blocking.** (a) true mid-scan locking (a worker blocks during execution) would rework the "worker never blocks mid-batch" scheduler invariant; (b) compute row-lock keys for point ops (PK/unique equality, INSERT literals) up front in `analyze_locks`. Chose **(b)** — delivers the headline concurrency win with no scheduler rework; the lock manager's hierarchy + deadlock detector generalize to a `Row` resource for free. Key-range locks stay table-based (documented).
3. **HashKey numeric hashing regime.** The engine's numeric equality is non-transitive at large magnitudes (Int/Decimal compare exactly via i128; any Float promotes to `f64`; `Decimal::to_f64` double-rounds), so no single hash matches `compare`. Chose **exact canonical rational for Int/Decimal, `f64` bits for Float, in separate hash classes** so `float = int/decimal` joins fall back to the nested loop. (An adversarial review caught the original all-`f64` hash dropping `bigint = decimal` matches > 2²³.)
4. **Correlated subqueries — per-row substitution, not resolver-threading.** Threading an outer scope + combined row through `exec_select`/`project`/`aggregate` (a `ChainedResolver`) is general but invasive given `project`'s `t.*` wildcard coupling. Chose **per-row substitution** (leave correlated WHERE subqueries un-folded; per outer row replace only outer-resolvable column refs with literals, inner column of the same name still wins; run the now-uncorrelated subquery). Correct inner-shadows-outer scoping, no restructure; scoped to WHERE over base/join subqueries.
5. **Adversarial review before merge** for the three correctness-critical PRs. It found and blocked, pre-merge: the Hash/Eq f64 bug (#71); three HIGH row-lock isolation holes — an IX→S `combine` dirty-read, a char-key-vs-numeric-literal under-lock, and a secondary-UNIQUE-index not serialized (#72); and an ambiguous-inner-column rebind (#73). All fixed and re-verified. Continued for #81 (grace-hash outer/DISTINCT spill — 3-lens review, zero findings) and #82 (collation — a 3-lens review + a verification sweep found **ten** fold-consistency bugs, all fixed and regression-tested before merge; the reviews were load-bearing here, catching a `_CS` UPDATE/DELETE data-loss bug and a spilling-GROUP-BY wrong-grouping bug that the initial test matrix missed).
6. **Stage 12 — grace-hash outer/DISTINCT spill chosen over key-range locks (deferred).** After finishing the spill story (#78–#81), the fork was (a) key-range (next-key) locks for finer SERIALIZABLE concurrency vs (b) other unfinished bullets. **Deferred (a)** despite the "choose performance" directive: making a SERIALIZABLE reader take `RangeShared` instead of `Table S` forces *every* `INSERT` (on all isolation levels) to also take a next-key `RangeInsert` lock — an extra index probe + lock on the write hot path — because a phantom insert can only be blocked if the inserter itself trips the reader's range lock. That regresses the common-case write path to speed up a rarely-used isolation level: a *net-negative* performance trade for typical workloads. Current table-granular SERIALIZABLE is already phantom-*correct* (a held `Table S` conflicts with any inserter's `Table IX`), just coarse. The genuine broad-concurrency win is the **sharded buffer-pool latch / partitioned lock manager** (replacing the single `Mutex<StorageFile>`), which is a larger, corruption-risky change deferred for user-steered work. Candidates recorded, not silently dropped.

7. **Stage 5 — case-insensitive equality via folded keys, autonomous storage change (user-approved).** The fork after #81: (a) query-layer CI equality only, or (b) full CI including the storage key layer. A query-only version is *impossible to ship cleanly* — `WHERE pk_char = 'abc'` can't fold in the filter but stay binary in the seek/uniqueness for the *same* column (all-or-nothing per column), so (a) would leave case-sensitive UNIQUE/PK/FK contradicting case-insensitive queries. Chose **(b)**, folding character key bytes at every store/lookup/probe site (a change to the on-disk key format, normally user-steered — explicitly approved this session). The alternative to key-folding, icu4x **collation sort keys**, is dependency-blocked (`icu_collator` 1.5 has no public sort-key API), so simple case-folding is the only route to CI-correct index keys today; it delivers CI equality/uniqueness/seeks but not locale *ordering*, which stays on the deferred sort-key work. Folding the row-lock hash *resolved* (not merely guarded) the coupling flagged below.

Resolved coupling (was "forward coupling to watch"): making WHERE equality collation-aware would have let a case-insensitive character **key** column match rows the binary row-lock key did not cover. #82 folds the row-lock hash itself (via `encode_key`), so CI-equal writers now serialise on one row lock — no exclusion needed.

**One-line status:** a working, transactional, concurrent SQL-Server-compatible engine — real ARIES storage/recovery, TDS wire protocol, most of the single-table + join/aggregate SQL surface, and the concurrency scale-out. Stages 1–8 are the core (done, with the gaps below); 9–12 are partial; 13–19 are unstarted.

### Notable divergences (what the 🟡 marks add up to)

- **Query engine hashes and spills (Stage 8).** *(Updated by PRs #71, #78–#81, #110–#111.)* Hash join (equijoins), hash aggregate, and hash DISTINCT replaced the old naive/O(n²) operators (#71). Spill is now built (#78–#81): a temp-extent `RowSpool` (self-describing cap-free row codec) backs an **external merge sort** for `ORDER BY`, **grace-hash aggregation** for `GROUP BY`, **grace-hash join for all kinds** (INNER/LEFT/RIGHT/FULL, with correct null-extension and `[left..right]` output orientation), and **grace-hash DISTINCT**, each spilling past a per-query memory budget instead of erroring or doubling memory. Input materialization is now bounded too (#110 single-table shapes, #111 join probe sides): every base-table input streams slice-by-slice or is the budget-bounded build side of a join; the sort/agg/join/distinct tests force-spill via a tiny test budget and assert byte-identical results to the in-memory path. Remaining under the streaming-scan item: statement-granular *output* streaming (needs static type derivation).
- **Concurrency: row locks for point ops, still coarse elsewhere (Stage 12).** *(Updated by PR #72.)* Point INSERT/UPDATE/DELETE now take Table IX + a `Row X`, so writers to different rows of one table run concurrently (with intent escalation and FK-parent / unique-index / character-key / float-key guards). Storage access still funnels through a single `Mutex<StorageFile>` (no sharded buffer-pool latches / partitioned lock manager / sharded txn table), and there are **no key-range locks** — SERIALIZABLE still leans on table locks for phantoms. Group commit's win shows only on slow disks. The deadlock detector runs synchronously when a batch parks (plus a 5 s timeout), not the planned 200 ms poll.
- **Collation: case-insensitive equality done, locale ordering pending (Stage 5).** *(Updated by PR #82.)* String **equality** is now case-insensitive by default everywhere — query operators and the storage key layer both case-fold (character key bytes are folded, so PK/UNIQUE/FK/seeks match case-insensitively), honouring explicit `_CS`/`_BIN`. Remaining: **ordering** is still icu-`compare` (ORDER BY) / binary (index keys), not full **collation sort keys** — so Swedish/Finnish *sort* order and `_AI` accent-insensitivity are unbuilt (blocked by `icu_collator` 1.5's missing sort-key API); collation **precedence** is simplified (any `_CS` operand forces exact, no conflict error); default collation still hardcoded.

- **Results stream end to end (Stage 6, done).** *(Updated by #101, #103, #105.)* The reply travels as a stream of `BatchEvent`s over an **unbounded** channel, and the executor emits each statement's events as it runs — a single-table bare-column SELECT streams rows in chunks straight off the sliced scan; `DONE_INXACT` is per statement. The plan's "bounded sinks" answer was **refuted** (backpressure onto a worker holds its table locks at the client's pace, and no code path can abort a running batch); the resolution was to drop the *bound*, not the streaming. Remaining, tracked in Stage 8's streaming-scan item: computed-column and join/aggregate/sort SELECTs still materialize their own statement's result before emitting it (needs static type derivation — COLMETADATA precedes the first row). A *hard* memory cap would be cap-and-spill or Stage 13's RCSI.
- **Prepared statements work (Stage 9).** *(Updated by #112.)* `sp_executesql` and the whole `sp_prepare`/`sp_execute`/`sp_prepexec`/`sp_unprepare` handle family work, with the handle returned via RETURNVALUE (pytds drives the family live in CI). There is deliberately no plan cache and no rebind machinery — every execute re-parses and re-binds against the live catalog, so DDL between prepare and execute is recompile-on-schema-change by construction (the plan's `catalog_version` design was moot on audit). All of it is wire-complete as of #113–#114: `sp_describe_first_result_set` (first-result-set contract, statically-derivable shapes, 11514 otherwise), DONEPROC/RETURNSTATUS/DONEINPROC framing with per-statement CurCmd command classes, and multi-RPC requests — adjudicated by pytds, go-mssqldb, and mssql-jdbc live in CI, plus ODBC sqlcmd and go-sqlcmd scripted runs.

### Smaller deferred items (self-contained follow-ups)

- **The hash-join collation pre-filter can disagree with eval on a reversed-written ON (Stage 8, pre-existing).** Found while reviewing #111 and *not* caused by it (formula-identical to the parent): `extract_equi_keys` normalizes each pair to (left column, right column), and the hash key's sensitivity combines in that normalized order, while eval's `comparison_sensitivity` combines in *written-operand* order — and `combine` favors its first operand when both sides are non-exact. So `ON r.c = l.c` (written reversed) joining a `_CI_AS` column to a `_CI_AI` column can fold the hash key under the *stricter* sensitivity than the one `matches` compares under: `'é'` and `'e'` land in different buckets, the candidate is never consulted, and a match the nested loop would emit is lost. Narrow (needs two different non-exact collations meeting in one equality, written right-to-left), but `_AI` collations are reachable. The fix is to combine the hash-key sensitivity in written order too — or better, make both sides agree on one canonical order.
- ~~A 5 s lock wait reports 1205, a deadlock that did not happen (Stage 12)~~ — **done (#119)**: an expired wait behind a live holder answers 1222; 1205 is reserved for real cycles, which at-park detection breaks instantly. Original note follows for the record. Found while reviewing #101 and *not* caused by it: `reap_expired` kills any waiter parked past `LOCK_WAIT_TIMEOUT` whose locks are still ungrantable, with the deadlock-victim error. So *any* batch running longer than 5 s — a big scan, today — makes every concurrent session on its table fail with a 1205 naming a cycle that never existed. SQL Server defaults `LOCK_TIMEOUT` to -1 (waiters wait; the operator kills the head blocker) and raises **1222** when an opt-in timeout fires; 1205 is only ever a real cycle. Distinguishing "blocked behind a live holder" from "in a cycle" is the fix, and it is a prerequisite for any design that lengthens a lock hold.

### Architecture notes

- The binder lives in `truthdb-core`, not behind the planned `CatalogProvider` trait in `truthdb-sql`.
- Stage 3's `spawn_blocking` execution model was superseded by the Stage 12 worker-thread pool.
- Search (ES) coexistence holds: search WAL events keep `entry_type=1`, relational records use type 3, one ring demultiplexed by type; the ES DSL is still reachable only via the native protocol.
