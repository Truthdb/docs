# TruthDB: S3 Workflow Checklist

Every S3 workflow, one numbered item each. When an item is done, overwrite its line with what was built.

## Buckets and objects

1. ✅ Manage buckets: CreateBucket (AWS naming rules), ListBuckets, HeadBucket, GetBucketLocation, versioning settings (Put/GetBucketVersioning), and DeleteBucket only when no object or open upload is left. Emptying a bucket is a listing followed by DeleteObjects on the client side (truthdb#202, #209).
2. ✅ Store objects: PutObject streams the body into the object engine in segments, up to 5 GiB. It verifies SigV4 chunk signatures, checksums and Content-MD5 as the body arrives. Replacing an object releases the old body after a grace period. Uploading many files is a client loop over PutObject (truthdb#203).
3. ✅ Multipart uploads: Create, UploadPart (a part can be retried or replaced), ListParts and ListMultipartUploads (to resume), Complete (a composite of the parts, no bytes copied; S3 order, ETag and size rules; at most 5 TiB) and Abort. Uploads left open for 7 days are aborted by garbage collection (truthdb#206).
4. ✅ Retrieve objects: GetObject streams a leased body; it supports single byte ranges (206/416), the If-Match, If-None-Match, If-Modified-Since and If-Unmodified-Since headers, and `versionId` (truthdb#203).
5. ✅ Inspect objects: HeadObject returns size, ETag (MD5), Last-Modified, content type, the stored system headers and `x-amz-meta-*`, without the body (truthdb#203).
6. ✅ Browse and organise: ListObjectsV2 and ListObjects support prefix, delimiter with CommonPrefixes, max-keys, start-after or marker, continuation tokens and `encoding-type=url`. A folder whose keys are all deleted is not listed, and each call scans a bounded number of rows (truthdb#204).
7. ✅ Copy and move: CopyObject shares the source body (no bytes copied) within or between buckets, with COPY/REPLACE metadata, copy-source conditions and `versionId`. UploadPartCopy shares a whole part or copies a byte range. Move is a copy followed by a delete on the client side. There is one region, so "across regions" does not apply (truthdb#207).
8. ✅ Delete objects: DeleteObject (a delete marker in a versioned bucket, a permanent delete with `versionId`) and DeleteObjects (up to 1000 keys, quiet mode, Content-MD5 or checksum required). Deleting everything under a prefix is a listing followed by DeleteObjects on the client side (truthdb#205).
9. ✅ Metadata and tags: system headers (content type, cache control, content disposition, encoding, language, expires) and `x-amz-meta-*` at write time and on GET/HEAD; CopyObject REPLACE to change them; tags through `x-amz-tagging` and Put/Get/DeleteObjectTagging, within S3's limits (truthdb#203, #208).
10. ✅ Versioning: enable or suspend; version ids on every response; ListObjectVersions with delete markers; GET by `versionId`; restore by copying an older version; recover a deleted object by deleting its marker (truthdb#209).

## Search

11. ✅ Exact lookup by bucket and key: HeadObject and GetObject, with 404 for a missing key and `x-amz-delete-marker` when its newest version is a delete marker (truthdb#203, #209; tests #210).
12. ✅ Prefix search via native listing: ListObjectsV2/ListObjects `prefix`, in UTF-8 byte order, with delimiters and pagination (truthdb#204; tests #210).
13. ✅ Substring or pattern match on names: `SELECT ... FROM sys.s3_objects(@bucket [, @prefix]) WHERE [key] LIKE ...` over TDS, a live inventory read from the object engine's own trees (truthdb#211).
14. ✅ Search by metadata: `sys.s3_objects`, `sys.s3_object_versions`, `sys.s3_object_tags` and `sys.s3_object_metadata` (size, storage class, content type, tags, user metadata), plus `sys.s3_journal(@bucket [, @after])`, the change journal in S3 Metadata's journal-table shape (truthdb#211, #213).
15. ✅ Full-text search inside object contents: opt-in per bucket (`s3 enable fulltext <bucket> [max_bytes]`), indexed in the background from the change journal, and queried from SQL with `sys.s3_search(@bucket, @condition [, @top])`, a CONTAINS-style condition ranked by BM25 (truthdb#215, #218, #220).
16. ✅ Query structured file contents: `sys.s3_read(@bucket, @key, 'csv'|'json'|'parquet' [, @options])` streams a stored object (or, with `{"prefix": true}`, every object under a prefix) as typed rows to any SQL client; Parquet files are read defensively against hostile input (truthdb#216, #217).
17. ✅ Semantic similarity search over embeddings: the S3 Vectors JSON API on the S3 port (SigV4 service `s3vectors`; vector buckets, indexes, Put/Get/List/DeleteVectors and QueryVectors) over a new vector engine on the shared log, with exact cosine or euclidean top-k search and S3 Vectors metadata filters; embeddings are supplied by the client, and a query returns all its results in one response (truthdb#221, #222).

## Operations

18. ✅ Access control: accounts, their users and access keys; AWS-style bucket policies and user policies (inline and managed, through an IAM API subset and STS GetCallerIdentity) evaluated as AWS does, scoping read/write/list/delete to buckets or prefixes, across accounts and for anonymous callers; Block Public Access per bucket and per account, on for new buckets; ACLs disabled (BucketOwnerEnforced) (truthdb#223–#227).
19. ✅ Sharing: presigned URLs (query-string SigV4, up to 7 days, for GET, HEAD, PUT, DELETE and part uploads, with `response-*` header overrides); browser form uploads (POST Object, the SDKs' presigned POST) under a signed policy document (expiration, eq, starts-with and content-length-range conditions, every field covered) or anonymously under a bucket policy; public read for selected content by bucket policy on a prefix or an object tag (truthdb#228, #230).
20. ✅ Data protection: the whole database encrypted at rest (pages AES-256-XTS with a MAC, log records and backups AES-GCM, standbys and restores included) under a database key wrapped by a master key from a key file or a wrap/unwrap command; online encryption of an existing database and rotation of both keys, resumable after a crash; SSE-S3 as that encryption, a bucket's encryption configuration, and SSE-C (customer-provided keys, over TLS, copies decrypting and encrypting again); Object Lock: retention in GOVERNANCE or COMPLIANCE mode, legal holds and event holds (variable retention), per object and as a bucket default, enforced wherever versions are removed (truthdb#231, #233–#235, #240–#242, #244, #246, #248, #250).
21. ✅ Lifecycle: the eight storage classes, kept with each version and shown everywhere; cold classes stored zstd-compressed (packed in place in the background, or as they arrive); GLACIER and DEEP_ARCHIVE readable only while restored (RestoreObject opens a time window, no copy); bucket lifecycle configurations as S3 validates them (prefix, tag and size filters; transitions, expirations, noncurrent-version rules, expired delete markers, abort of incomplete uploads), applied by a daily background pass, at most one action per version a day, through the engine's own paths so Object Lock applies; `x-amz-expiration` and `x-amz-restore` headers; every change in the journal, which consumers follow from their own place (truthdb#251–#257).
22. ✅ Synchronise and migrate: the AWS CLI (`aws s3 sync`, `cp --recursive`, `mv`, `rm`) and rclone sync both ways, multipart and default CRC64NVME checksums included; presigned URLs carrying headers in their query as the SDKs write them; GetObject and HeadObject by part number; `truthdb-cli s3 ls|mb|cp|sync|rm` (filters, --delete, --dryrun, credentials from flags, environment or ~/.aws/credentials); server-side imports from another S3 service (`s3 create import`), skipping objects already there alike, resumable after a crash without copying anything twice, shown in `sys.dm_s3_imports` (truthdb#258–#263).
23. ✅ Event notifications: bucket notification configurations as S3 validates them (event types, prefix and suffix filters, overlap rules, a test event), each change of a bucket's objects (created, removed, restored, transitioned, expired, retention set) sent as S3 event JSON, once, in the order of the journal, to a stream topic of the bucket owner's account on a new streams engine on the shared log (partitions, retention, consumer offsets). Topics are read through `sys.stream_read`, consumed as SQL queues (`sys.sp_s3_queue_receive`, `_ack` and `_change_visibility`: visibility timeouts and redelivery), posted to webhooks (HMAC-signed, retried with backoff, dead-lettered, shown in `sys.dm_s3_webhooks`), or read by Kafka consumers over TLS with SASL PLAIN (consumer groups and committed offsets). Topic ARNs map to stream topics, queue ARNs to SQL queues and function ARNs to webhooks (truthdb#264–#269).
24. ✅ Bulk jobs: S3 Batch Operations through the S3 Control API (CreateJob, idempotent by client token, with ConfirmationRequired; DescribeJob, ListJobs, UpdateJobStatus, UpdateJobPriority), on the objects a CSV manifest lists (pinned by its ETag) or a manifest the job generates from a bucket's listing and filters (written out when asked); copy, replace or delete tags, restore, Object Lock retention and legal hold, and LambdaInvoke (a signed POST to a stream topic's webhook); every task authorized as its creator's own request would be, run once across a crash (invocations at least once), the job failing past half its tasks failed; a completion report written to a bucket; `sys.dm_s3_batch_jobs` (truthdb#270–#273).
25. ✅ Serve content: CORS (Put/Get/DeleteBucketCors; preflights answered before authentication; the allowed `Access-Control-*` headers and `Vary: Origin` on every answer to a request with an Origin, errors included); virtual-hosted addressing under `[s3] domains` (the bucket from the Host, the path the whole key, S3 Control by its account host); caching that CDNs and proxies rely on (conditional requests, Range and versionId together answered as specified, If-Range per RFC 9110, proven behind nginx's proxy cache and slice module); static website hosting: Put/Get/DeleteBucketWebsite and `<bucket>.s3-website.<domain>` serving what the public may read, anonymously, with index and error documents, routing rules, RedirectAllRequestsTo, object redirects (`x-amz-website-redirect-location`) and HTML error pages (truthdb#274–#280).
26. ✅ Monitoring and audit: storage usage per bucket and storage class (current and noncurrent versions, delete markers, upload parts), counted in the same transaction as each change, and request counts, errors, bytes and latency, in `sys.dm_s3_bucket_usage`, `sys.dm_s3_storage`, `sys.dm_s3_requests` and `sys.dm_s3_request_latency`; an admin listener with Prometheus `/metrics`, `/healthz` and `/readyz` (optional bearer token); bucket metrics configurations (prefix, tag and access-point filters) and their history, rolled up per minute, five minutes and hour, read through CloudWatch's ListMetrics, GetMetricStatistics and GetMetricData; server access logs in S3's record format, delivered as objects to a bucket of the same owner; an API activity log of management events kept 90 days (`sys.dm_s3_api_activity`, CloudTrail LookupEvents), and trails delivering CloudTrail log files with event selectors for management and S3 data events; S3 Inventory reports (configurations as S3 validates them, daily or weekly CSV or Parquet lists with their manifest, checksum and Hive symlink, made once across a crash) (truthdb#281–#297).

## Replication

27. ✅ Configure replication: Put/Get/DeleteBucketReplication with S3's V2 rules (ID, Priority, Status, Filter, DeleteMarkerReplication, Destination with Bucket, Account and StorageClass, and Role), validated as S3 validates them. It needs versioning on the source and on a destination of this server, and versioning cannot be suspended while a configuration is set. Replication acts as the one who put the configuration: they need `s3:GetObjectVersionForReplication` on the source version and `s3:ReplicateObject` (`s3:ReplicateDelete` for markers) in the destination, checked each time a replica is made. Rules without a Filter (the V1 schema), KMS encryption and `ExistingObjectReplication` are refused (501); AWS no longer offers the last, and Batch Replication replaces it (truthdb#298).
28. ✅ Same-region replication: each version written in a bucket with a configuration is queued, in the same transaction, to every destination a rule names. A runner makes the replicas in order: on this server a replica shares its source's body and keeps its version ID, time, metadata, tags and Object Lock settings. `x-amz-replication-status` is PENDING, COMPLETED, FAILED or REPLICA on GET and HEAD and in inventory reports. Tag changes replicate; Object Lock changes after the replica is made do not, since a replica's lock is its destination's own once written. Permanent deletes never replicate. Version state (attributes, locks, restores) was re-keyed by bucket, key and version first, online and resumably, so a replica can keep its source's number (truthdb#299–#300).
29. ✅ Cross-region replication: to a bucket on another S3 service (another TruthDB server, or AWS), registered with `s3 create remote bucket <name> <account> <endpoint> <region> <key> <secret> [ca_file]` and shown in `sys.dm_s3_remote_buckets` without its secret. Replicas are sent through the S3 client, in parts past 8 MiB, in order per remote, waiting with backoff while it is down and FAILED on a lasting refusal. A remote replica is a plain write: it gets the remote's own version ID and no REPLICA mark, and tag changes are not sent after it. A crash between a send and its record sends it again (at least once), and Batch Replication of a version sends it again as a new version there (truthdb#301).
30. ✅ Cross-account replication: to another account's bucket, as its bucket policy grants the configuration's creator `s3:ReplicateObject` (FAILED otherwise). `Account` must name the destination's owner, `AccessControlTranslation` Owner=Destination is kept, and replicas are always the destination owner's, as every bucket here has bucket-owner-enforced ownership. A destination's owner is pinned when the configuration is put, so a bucket deleted and made again by another account takes no replicas (truthdb#302).
31. ✅ Selective replication: Filter by Prefix, Tag, or And (a prefix and tags), matched against a version's tags when it is written. Priority decides between overlapping rules of the same destination. SourceSelectionCriteria ReplicaModifications syncs a replica's tag changes back when both buckets ask for it, and a two-way sync ends. Objects under customer-provided keys (SSE-C) are replicated on this server (not to a remote); SseKmsEncryptedObjects Enabled is refused, as there is no KMS (truthdb#303).
32. ✅ Replication to multiple destinations: one queued replication per destination, each counted. As S3 shows it, a source version is FAILED once one destination failed, PENDING until every one has it, then COMPLETED (truthdb#304).
33. ✅ Batch Replication: the batch operation `S3ReplicateObject`, authorized as the job creator's `s3:InitiateReplication`, queues each object's replication again to the destinations its bucket's rules name: NONE (existing), FAILED (a retry), COMPLETED (a backfill) and REPLICA (onward) versions. Generated manifests list every version and take EligibleForReplication and ObjectReplicationStatuses, with `s3:GetReplicationConfiguration` on the source. An object no rule replicates fails SrcObjectNotEligible. A task succeeds once its replications are queued, and is run once across a crash (truthdb#305).
34. ✅ Delete-marker replication: `DeleteMarkerReplication` Enabled (refused for a rule that filters by tags, as S3 refuses it) replicates the markers deletes make, not those of lifecycle expiration. On this server a marker replica keeps its source's version; to another service it is a DELETE, sent only to a bucket with versioning enabled. Permanent deletes by version ID never replicate. A marker has no replication status (truthdb#306).
35. ✅ Replication monitoring: Metrics and ReplicationTime (15 minutes only) per destination; each rule's backlog (operations, bytes, failures, the oldest queued) counted in the queue's own transactions and shown in `sys.dm_s3_replication` and as Prometheus gauges. Rules that measure theirs are sampled once a minute into CloudWatch's ReplicationLatency, BytesPendingReplication, OperationsPendingReplication and OperationsFailedReplication by SourceBucket, DestinationBucket and RuleId, and send the `s3:Replication:*` events (failed with S3's failure reason, not tracked, missed threshold, replicated after threshold) as S3's own, eventVersion 2.2. A measured rule needs an ID. Nothing is faster with replication time control (truthdb#307–#308).
36. ✅ Change or stop replication rules: a configuration replaced, a rule disabled or a configuration deleted drops the queued work no rule sends any more, including work waiting for a remote that is down. Replicas made and the statuses recorded stay, and a version whose remaining work is dropped is COMPLETED by what was made, or has none (truthdb#309).

## Not covered by the source conversation

37. ✅ Conditional writes: `If-None-Match: *` (create only if absent) and `If-Match` (compare-and-swap on the ETag) on PutObject, CopyObject's destination and CompleteMultipartUpload, decided in the write's own transaction. The first write to finish wins; a later one gets 412, and 409 ConditionalRequestConflict when the version it names is deleted while its body arrives. Conditional deletes: DeleteObject's `If-Match` and DeleteObjects' per-object `ETag` (412 on a mismatch; a delete compared with an ETag also needs `s3:GetObject`). The policy keys `s3:if-match`, `s3:if-none-match` and `s3:ObjectCreationOperation` are set. `If-None-Match` other than `*` is refused (501), as are the last-modified-time and size conditions, which AWS supports only on directory buckets (truthdb#310).
38. ✅ Strong read-after-write consistency for all operations, stated and tested as a guarantee: any read made after a write's answer, on any connection, sees it (creates, overwrites, deletes, tags, metadata, copies, multipart completions); a read during an overwrite sees one version whole; an acknowledged write is durable, as each transaction is synced to the log before its answer. Stronger than AWS: bucket configurations (versioning, a deleted bucket) are strongly consistent too. Concurrent writes to one key: the last to commit wins. A replication standby lags by its replication delay (truthdb#311).
39. ✅ Checksums and integrity: CRC32, CRC32C, CRC64NVME, SHA-1 and SHA-256 are verified on upload, kept with the object (CRC64NVME computed when none is sent, as AWS attaches it) and returned on PUT, on GET and HEAD with `x-amz-checksum-mode`, in CopyObjectResult and in GetObjectAttributes. The other algorithms AWS names (MD5, SHA-512, XXHASH) are refused with 501. Multipart uploads take an algorithm and a type: FULL_OBJECT values are combined from the parts' CRCs, COMPOSITE ones are the checksum of the parts' checksums with `-N`; parts' checksums are checked at completion, listed by ListParts, and kept with the object for GET and HEAD by part number. Copies keep their source's whole checksum or compute one as S3 does (`x-amz-checksum-algorithm`, CRC64NVME for a source with none). GetObjectAttributes, the batch operation S3ComputeObjectChecksum (its report carries each object's checksum) and the inventory's ChecksumAlgorithm column read them (truthdb#312–#316).
40. ✅ Directory buckets (S3 Express One Zone's): CreateBucket of a `<base>--<zone-id>--x-s3` name with its Directory configuration, ListDirectoryBuckets, HeadBucket's location headers and S3 Express ARN, and EXPRESS_ONEZONE as every object's class. They take only the operations, headers and listing forms AWS lists for them; the rest get 501 (or 400 for a version id but `null`, a delimiter but `/`, a prefix not ending in it). CreateSession gives five-minute session credentials, kept in memory, bound to the bucket (its owner and creation) and its mode; requests signed with them (`x-amz-s3session-token`) act in that bucket only, a ReadOnly session only reads. Authorization is S3 Express's: `s3express:` actions on the bucket's ARN, and `s3express:CreateSession` (with `s3express:SessionMode`) for objects; CloudTrail records them as S3 Express's. RenameObject renames an object atomically, with its conditions and an idempotent client token; appends (`x-amz-write-offset-bytes`) add a part at the object's size, its whole CRC combined or a composite SHA. Nothing is faster, ETags are MD5-based, listings are sorted, and there are no real zones (truthdb#317–#320).
41. ✅ Table buckets (S3 Tables): table buckets, namespaces and tables under the `s3tables` API (signing service `s3tables`), with GetTableMetadataLocation and UpdateTableMetadataLocation as a compare-and-swap on the version token, and table bucket and table policies, cross-account. A table's data and metadata live in its own storage bucket (`<table id>--table-s3`), reachable through S3 with GetTableData and PutTableData only, and removed with the table. CreateTable writes the table's first Iceberg metadata file. The Iceberg REST catalog (`/iceberg/v1`) serves PyIceberg and Spark, signed with SigV4: namespaces, tables, and commits checked as Iceberg applies them. Maintenance is configured per table bucket and per table, and runs in the background:
    - snapshot management expires snapshots by count and age;
    - unreferenced file removal marks unreferenced objects noncurrent and deletes them after nonCurrentDays;
    - compaction rewrites small Parquet files by Iceberg's bin-pack rules. It applies position and equality deletes, and sorts and z-orders by the table's sort order. Each rewrite is committed as a `replace` snapshot only when every row is accounted for.

    Not built: Avro and ORC data files, and the Iceberg v3 format. Compaction re-runs on a conflict, without rebasing. There is no AWS Lake Formation or Glue integration (truthdb#321–#331).
42. ✅ Access Points: the S3 Control API (CreateAccessPoint, GetAccessPoint, ListAccessPoints, DeleteAccessPoint, access point policies and their policy status), with an alias per access point, Block Public Access settings fixed at creation, and access points on another account's bucket named with its owner. Only the Internet network origin is built, and VPC configurations, tags and directory buckets are refused. Requests reach an access point by its host (`<name>-<account>.s3-accesspoint.<region>.<domain>`) or by its alias in place of the bucket's name. They take the object operations and the bucket reads AWS lists, and act on its bucket while that bucket is still the one it was made for. Authorization needs both sides to allow:
    - the access point's policy and the caller's own policies, on the access point's ARN;
    - the bucket's policy, on the bucket's ARN, with a grant to an account counting as that account's policies allow;
    - both sides see `s3:DataAccessPointArn`, `s3:DataAccessPointAccount` and `s3:AccessPointNetworkOrigin`, and a RestrictPublicBuckets of the access point, the bucket or its owner's account restricts both.

    Requests through access points count for their bucket in the request metrics, in metrics configurations filtered on `AccessPointArn` (single-object requests only), in its access log (the Access Point ARN field) and in CloudTrail (an `AWS::S3::AccessPoint` resource). The bucket's CORS configuration answers for them. An account that owns neither the access point nor the bucket sees only the name it gave in its own events. Bucket names with an `s3-accesspoint` label are refused, so that no bucket shares an access point's host. Not built: HTTPS enforcement on access points, copy sources named by an access point, form uploads (POST Object) through an access point, and VPC origins. Which ARN identity policies must allow is unconfirmed against AWS (truthdb#332–#334).
43. Object Lambda: transform objects on read.
44. Requester Pays buckets.
45. Transfer acceleration.
46. Storage analytics dashboard (Storage Lens equivalent).
47. Mount a bucket as a filesystem (Mountpoint equivalent).
