# TruthDB Basic Search Plan

## Purpose

This document describes the first TruthDB implementation plan corresponding to the scenario in [ELASTICSEARCH_BASIC_SEARCH_SCENARIO.md](ELASTICSEARCH_BASIC_SEARCH_SCENARIO.md).

The goal is not to clone Elasticsearch. The goal is to implement the smallest useful TruthDB vertical slice that can perform the same basic workflow:

- create an index
- insert JSON documents
- run a text search
- run a filtered search

## Scope

This first implementation will run over the existing TruthDB TCP listener and CLI.

It will not introduce HTTP yet.

That means the scenario will be functionally similar to the Elasticsearch scenario, but the commands will be issued through `truthdb-cli repl` instead of `curl`.

## Current State

Today, TruthDB can:

- start the server
- accept client connections
- exchange hello and heartbeat messages
- create or open the storage file

Today, TruthDB cannot yet:

- create indexes
- store documents
- search documents
- return structured query results

At the moment all `CommandReq` messages return `not implemented`.

## First User-Facing Commands

The first version should accept simple command verbs followed by a JSON body.

Proposed commands:

```text
create index products {
  "mappings": {
    "properties": {
      "name": { "type": "text" },
      "category": { "type": "keyword" },
      "price": { "type": "float" },
      "description": { "type": "text" }
    }
  }
}
```

```text
insert document products {
  "name": "Red Running Shoes",
  "category": "shoes",
  "price": 79.99,
  "description": "Lightweight shoes for road running"
}
```

```text
search products {
  "query": {
    "match": {
      "description": "running shoes"
    }
  }
}
```

```text
search products {
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "comfortable" } }
      ],
      "filter": [
        { "term": { "category": "shoes" } }
      ]
    }
  }
}
```

## Why This Command Shape

This is the fastest path to a working feature because:

- the transport already exists
- JSON is a natural fit for mappings and documents
- the commands preserve the Elasticsearch mental model
- it avoids designing a SQL dialect too early

## Required Engine Capabilities

To support the first scenario, TruthDB needs these core capabilities.

### 1. Shared Engine State

The server needs a shared process-level engine instead of a stateless per-connection dispatcher.

That engine must hold:

- index definitions
- field mappings
- stored documents
- text indexes
- exact-match indexes

### 2. Catalog

TruthDB needs a catalog for index definitions.

For v1, the supported field types should be:

- `text`
- `keyword`
- `float`

No dynamic mapping is needed in the first implementation.

### 3. Document Storage

TruthDB needs to store original JSON documents by document ID.

For v1:

- autogenerated document IDs are sufficient
- explicit document IDs may be added later

### 4. Text Search

TruthDB needs a basic inverted index for `text` fields.

For v1, a simple approach is enough:

- lowercase normalization
- whitespace tokenization
- term-to-document posting lists

No stemming, stopword removal, or analyzers are required yet.

### 5. Exact Filters

TruthDB needs exact-match lookup for `keyword` fields.

That supports filters such as:

```text
category = "shoes"
```

### 6. Search Execution

TruthDB needs a minimal query evaluator that supports:

- `match`
- `term`
- `bool.must`
- `bool.filter`

For relevance scoring, the first version can use a simple strategy such as:

- score by number of matched terms

This is enough for the first scenario and avoids premature ranking complexity.

### 7. Structured Results

The protocol needs to return more than a single success string.

Search results should include at least:

- document ID
- score
- original document body

The first implementation may return JSON-encoded results inside the current response message field, but that should be treated as a temporary bridge. A typed result payload is the better long-term design.

### 8. WAL Persistence

TruthDB's architectural direction is that the WAL is the source of truth.

For this feature, each mutation should be represented as a WAL event:

- `CreateIndex`
- `InsertDocument`

On startup, TruthDB should replay those WAL events to rebuild:

- the catalog
- the document store
- the search indexes

This keeps the feature aligned with the current TruthDB storage direction.

## JSON Error Handling

If a command contains malformed JSON:

- the whole command must fail
- nothing must be applied
- the client should receive a clear parse error

TruthDB should not partially apply malformed writes.

That is the correct first behavior and is consistent with the intended Elasticsearch-like mental model.

## REPL Implications

The current REPL sends each line on Enter.

That is acceptable only if commands stay on one line, which becomes awkward for JSON bodies.

The likely next CLI improvement is buffered multiline input with one of these rules:

- execute when braces are balanced and the command is complete
- execute on an explicit terminator such as `;`
- execute on a command such as `\\g`

This is not strictly required for the engine work, but it will matter quickly once JSON commands become real.

## Implementation Phases

### Phase 1: Shared Engine Skeleton

- introduce a shared engine object
- pass it into connection handlers
- route command requests into the engine

### Phase 2: Command Parsing

- parse `create index <name> <json>`
- parse `insert document <index> <json>`
- parse `search <index> <json>`

### Phase 3: In-Memory Catalog And Documents

- create indexes
- validate mappings
- assign document IDs
- store documents in memory

### Phase 4: In-Memory Search

- build text and keyword indexes
- implement `match`
- implement `term`
- implement `bool.must` and `bool.filter`
- return ordered results

### Phase 5: Persistence

- encode mutation events into WAL payloads
- replay WAL on startup
- rebuild in-memory state from replay

### Phase 6: REPL Usability

- support multiline command entry
- improve result rendering
- improve error messages

## Explicit Non-Goals For V1

The first version should not attempt:

- HTTP endpoints
- shards or clustering
- replicas
- advanced analyzers
- aggregations
- sorting options
- updates or deletes
- dynamic mappings
- refresh semantics like Elasticsearch
- SQL compatibility

## Success Criteria

This feature is successful when a user can:

1. start `truthdb`
2. open `truthdb-cli repl`
3. create a `products` index with `text`, `keyword`, and `float` fields
4. insert a few product documents
5. run a text search against `description`
6. run a filtered search on `category`
7. stop and restart TruthDB
8. repeat the search successfully after WAL replay

## Recommended First Milestone

The first milestone should be:

- single-node
- in-memory engine
- WAL-backed mutation replay
- multiline REPL support
- exactly the commands needed for the basic search scenario

That is small enough to ship quickly and large enough to prove the TruthDB architecture can support a real document-search workflow.
